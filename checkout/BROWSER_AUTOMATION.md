# 浏览器付款执行层（进行中）

目标仍是接入 hypitoken 的完整浏览器付款流程，不是仅生成链接。当前已接入准备、填卡、预览、显式确认提交和严格结果查询，跑通本地合成上游的完整浏览器链路；另支持运行 Go 的本机显示原订单窗口。远程用户验证接管与真实官方联调尚未完成，不能作为生产可用或真实付款成功证明。

## 本地可见订单窗口

独立程序增加 `-local-browser-window`，仅接受 IP 字面量回环监听地址，要求浏览器服务已启用且 Go 进程有桌面显示环境。必须在接受订单前配置；不会启用原本关闭的付款提交开关。普通生产启动默认仍为无头。

此模式直接显示同一个订单 Chromium，用户在运行 Go 的电脑上完成验证后回到助手查询结果；不另开登录态、不改变出口、不重放验证请求。远程访问网站不会把窗口显示到访问者电脑。请保持订单窗口打开；助手页离开时只关闭未提交的浏览器，已尝试提交的保留到原定超时，原有 15 分钟生命周期不延长。应用防重付只约束自动提交，不能阻止用户在原生浏览器内自行再次点击 Subscribe。

此功能不解决首次建单前的登录挑战恢复，也不扩展出口域名允许列表；需要未知银行域名的验证可能仍被拒绝。真实验证和真实扣款未在此模式中完成。

## 提交后刷新与原浏览器恢复

提交前仅把结账编号和处理实体写入当前标签页的 sessionStorage；不存 Session、代理、卡、账单、flow。刷新后展示原编号并锁定新付款，用户重新提供原 Session 与原代理，通过 `/api/recover` 恢复查询。关闭整个标签页可能丢失 sessionStorage，因此仍需保存结账编号。

恢复必须先通过持久化付款记录的所有权核验。匹配的活动浏览器存在时使用其原查询客户端，检查代理一致性，不新建 Chromium、不重新报价/填卡/提交；错误或忙碌不回退其他出口。核验成功后回传原 flow，用于状态、预览和显式关闭，仍锁定付款。观察器只能解释 pending，不能覆盖已核验成功或金额矛盾。

已关闭/重启后无活动浏览器的恢复仍走持久化查询路径；新记录的网络绑定与旧记录限制见下节。原浏览器的页面状态、登录 Cookie 和验证进度不会因此重建。

## 重启后恢复的网络绑定

浏览器与协议提交入口均传入独立的 `Ledger.WithNetwork` 句柄，在同一份排他且 fsync 的付款确认记录中保存版本化网络摘要：用户原始代理配置的摘要，以及实际经过公网校验、固定 IP 后端点的摘要。空代理也有明确绑定，不能与缺少字段的旧记录混淆。句柄不修改共享 Ledger；记录不包含代理 URL、用户名、密码或明文 IP。

没有活动浏览器时，恢复首先核验所有权和原代理配置，再解析并校验公网代理 IP，最后核对端点摘要。两步通过后才建立出站客户端；代理缺失、增加、变更、解析结果变化或未知记录版本均停止查询，不回退直连、不轮换 IP。此约束不能控制代理供应商背后的出口轮换，也不证明浏览器页面在重启后仍可恢复。

旧记录继续阻止重复付款；若原活动浏览器仍存在，可按内存中的原网络继续查询。没有活动浏览器且旧记录缺少网络绑定时，不猜测原出口、不自动迁移记录，需由用户通过原官方结账页核对。发布或回滚时不可使用会忽略网络绑定的旧服务继续自动恢复查询。

## 最新：KC 链路对照与本地完整集成

在环境权限更新、用户明确要求参照上一级 KC 项目本地跑通后，新增 `/api/browser/submit`，以 `GPTPAY_BROWSER_SUBMIT_ENABLED=true` 独立启用；默认关闭，启用准备接口不会启用付款。网页先填卡，再要求用户确认账号、套餐及含税金额。提交不携带第二份卡数据，锁定订单后仅查询结果。错误、超时和未知状态不自动重付；已有 Ledger 记录也禁止继续改表单或报价。

本地目录实际为 `KC-PAY-GPT`。参考 `stripe-payment.js` 的填表、提交、等待结果阶段；没有执行其代码、接入供应商、自动换卡、解验证码或采用跳转即成功判断。已按其“填卡后再填账单”的阶段划分，补齐初次账单控件缺失时的有界准备流程；真实官方页面的更多动态变体仍需联调。

新增 `gptpay_integration` 构建标签下的跨仓集成支架：实际网页与 handler、cc-core、真实 Chromium 启动/填表/原生点击/状态请求均参与；只有上游页面和响应为合成数据，所有外部拨号被拒绝。普通生产构建不包含支架，不得用此标签构建生产包。详见 [本地链路验证](../docs/gptpay-local-browser-e2e-20260916.md)。

## 最新：提交后状态观察

提交后状态观察已补齐基础实现：只在持久化防重付记录建立后开始观察已绑定浏览器及卡片 iframe。旧式 ChatGPT confirm 必须携带当前结账编号，其响应显式关联 PaymentIntent 后才接受该 Intent 的 confirm / verify_challenge 结果，且金额和币种必须相符。Payment Page 分支仅接受明确结账 ID 和展开的 PaymentIntent 对象；实际抓包中该响应正文不可用，因此该分支尚无真实兼容性证明。不会因遇到一个 Stripe 请求就认定它属于本单。

观察器只保存标准化进度与白名单错误码；网络事件队列与响应缓冲有上限，不记录 HAR、原始响应、client_secret、卡数据或验证码内容。成功仍只认严格订单对账，Stripe succeeded 最多表示 processing。网站仅在本单已尝试且对账为 pending 时使用观察结果；对账错误、已核验 paid 和 expired 不被覆盖。真实 Chromium 合成整链路增加 requires_action 和验证失败分支，两者通过；29 项前端测试通过。交互接管未启用，页面明确提示保持当前会话，不建议换浏览器重付。

## 当前实现

- Go 使用固定版本 chromedp 直接启动 Chromium，无 Node.js 服务；每单独立进程和隐身上下文，拒绝 root / 禁用沙箱启动，不复用用户的现有浏览器。
- `Start` 接收 Chromium 路径、语言、时区、生命周期、固定 SOCKS5 地址。默认 en-US / America/New_York / 15 分钟；语言与时区可由调用方明确选择，不据此修改用户账单国家。
- `Create` 接收 Session JSON 和国家/币种/套餐；仅导入其中的登录 Cookie，不导入抓包里的 clearance / observation / 验证令牌。由页面正常 fetch 创建结账，保留真实浏览器行为，不伪造安全验证结果。每个 Browser 只允许创建一次。
- `FillBilling` 只填写调用方提供的账单数据，检查 Token 所有权及精确结账路径；匹配不到或存在多个控件时返回 `missing`，不猜测、不自动点击 Subscribe。
- `FillCard` 检查本单所有权和结账路径，支持主页面及可见 Stripe 跨进程 iframe 中的卡号、合并有效期、CVC 控件。字段不唯一时不部分填写；通过浏览器输入事件填入，不点击 Subscribe。分开的月份/年份控件等动态变体尚需补齐。
- `Preview` 返回本单页面的内存 JPEG，只读显示；不持久化图片。预览接口与其他浏览器接口使用相同的鉴权和订单绑定。
- `QueryClient` 在同一浏览器上下文中执行本单状态 GET 和税费 POST，复用 cc-core 已有的报价金额/币种/套餐/账号验证。此适配器拒绝旧版 Pay、任意 URL、订阅修改及其他订单请求；403 原样分类为访问被拒，不自动切回 Go 直连或伪装成功。
- 私有 CONNECT 中继保留端到端 TLS。空代理显式直连；SOCKS5 支持用户名/密码和由代理解析目标域名，失败不回退。代理参数必须来自 hypitoken 已校验并固定的公网 IP，禁止浏览器重新解析代理主机。
- 限制目的域、443 端口、连接数量和时长；禁止 QUIC 和非代理 WebRTC UDP，取消 Chromium 的隐式 localhost 代理绕过。未知银行/支付域名会被拒绝，需基于正常流程证据显式扩展策略。
- 生命周期结束或 `Close` 关闭浏览器及中继连接。隐身上下文中的 Cookie 不跨订单共享；无 Session / 卡信息日志、录像、HAR 持久化或第三方供应商调用。
- Chromium 子进程使用 `/usr/bin/env -i` 和显式白名单环境，不继承服务密钥、HTTP(S)/ALL_PROXY、HOME、动态加载器或 TLS 密钥日志变量。仅保留固定 PATH、语言/时区/临时目录；有界面模式另保留显示会话设置。Linux 保留父进程退出时终止浏览器的信号配置。此措施不隔离同一系统用户可读的文件或 `/proc`，不能替代独立 OS 权限边界。

Chromium 的配置是应用层出口约束，不等于已完成生产网络隔离验收。部署还需要专用非特权系统用户、受控的临时目录/内存与 core dump 配置、仅允许中继出口的系统级策略及实测。CDP 和中继只监听回环，禁止通过 Caddy 暴露。

本机 Chromium 153 创建空隐身上下文时需要 `Target.createTarget(newWindow=true)`。已显式创建窗口，避免 chromedp v0.14.2 默认 `false` 引起的 `no browser is open`。该行为与 [chromedp 的问题记录](https://github.com/chromedp/chromedp/issues/1601) 一致。

## hypitoken 接入进展（2026-09-16）

新增 `internal/gptpay/browser_api.go`。独立开关 `GPTPAY_BROWSER_ENABLED` 默认关闭；`GPTPAY_CHROMIUM_PATH` 必须指向可执行文件，服务必须使用非 root 用户。`GPTPAY_BROWSER_LIMIT` 默认 2，范围 1–8；单会话寿命 15 分钟，每个 Token 同时只允许一个浏览器。

| POST 路由 | 内容 |
| --- | --- |
| `/api/browser/create` | Session JSON（必须同时含 accessToken、sessionToken）、selection、可选 proxy；返回 flow 和 checkout |
| `/api/browser/quote` | 同一 Session / proxy / flow、billing；返回已核验报价 |
| `/api/browser/fill-billing` | 同一 Session / proxy / flow、billing；返回 filled / missing，清除旧报价 |
| `/api/browser/fill-card` | 同一 Session / proxy / flow、card、当前报价金额和币种；仅填写卡片，不确认付款 |
| `/api/browser/preview` | 同一 Session / proxy / flow；返回内存 JPEG 与尺寸，只读显示 |
| `/api/browser/status` | 同一 Session / proxy / flow；仅查询支付结果 |
| `/api/browser/close` | 同一 Session / proxy / flow；关闭并释放进程 |

所有路由受来源、JSON 大小、速率、并发、Token 所有权和固定代理校验保护；仅 fill-card 接受卡信息，新增 submit 独立接受付款确认。会话退出清理由 `cmd/gptpay` 的 `Service.Close()` 执行。原 `/api/pay` 保持协议执行；浏览器模式页面使用新的 `/api/browser/submit`，不回退到协议付款。

Chrome DevTools MCP 已完成一次本地 UI 契约验证：合成资料粘贴、创建、填写账单、报价、填写卡片、1280×900 JPEG 预览、关闭浏览器。填写和关闭后 Session、卡号、有效期和 CVC 输入保持非空。该验证使用真实 HTTP handler 与网页资源，但 worker 为测试替身，不访问真实支付上游；不能据此宣称实际付款成功或 403 已解决。测试服务已正常停止，测试标签页已关闭。前端四个测试文件通过。
